# Подключение Яндекс Метрики к RentZal

## Что уже реализовано

- `/privacy/` — проект политики обработки данных.
- `/analytics-consent/` — отдельное согласие на аналитику.
- `/cookies/` — описание cookie и управления выбором.
- Настройки cookie доступны внизу каждой страницы. Согласие и отказ равноправны; закрытие уведомления не даёт согласия.
- До явного согласия нет загрузки tag.js, пикселя noscript или preconnect к Яндексу.
- Запуск счётчика только после успешной записи согласия сервером и сохранения решения в браузере. При ошибке — без аналитики.
- Отзыв выгружает код перезагрузкой, очищает доступные cookie `_ym_*` и синхронизируется между вкладками.
- Вебвизор, карта кликов, отслеживание ссылок, электронной коммерции и Яндекс Тег Менеджер выключены. Просмотр передаётся без query/hash и реферера. Это не делает данные автоматически анонимными.

## Счётчик в аккаунте владельца

1. Войти в https://metrika.yandex.ru/ под личным аккаунтом владельца.
2. Создать счётчик RentZal, указать адрес действующего сайта. При переносе обновить адрес и в Метрике, и в конфигурации.
3. Отключить Вебвизор/аналитику форм, автоматические цели, сбор контактов, рекламные интеграции и Тег Менеджер. Включить маскировку IP в дополнительных условиях обработки данных. Не включать новые функции без пересмотра документов и согласий.
4. Скопировать числовой ID в `privacy.config.json` → `counterId`. Это публичный номер, не пароль. API-токен для установки счётчика не нужен.
5. После запуска открыть счётчик → отчёты посещаемости (раздел «Посещаемость» или сводка), выбрать период. «Посетители» и «Визиты» — разные показатели. Метрика оценивает браузеры/устройства; это не точное число физических лиц.

В отчёты попадут только согласившиеся посетители с работающим счётчиком. Отказавшиеся, блокировщики и ошибки сети дают неполную статистику. ID счётчика сам по себе не даёт доступа к отчётам — доступ принадлежит аккаунту, создавшему счётчик.

## Перед включением

1. Заполнить почтовый адрес оператора, который допустимо публиковать. Проверить ФИО и контактный email.
2. Определить подходящее размещение. Проверить локализацию по ч. 5 ст. 18 152-ФЗ, журналы хостинга/CDN, почтовый сервис, получателей и сроки хранения. GitHub Pages — иностранная инфраструктура; баннер не решает вопросы обработки технических данных провайдером. Для этого варианта подготовлен сервер для размещения на выбранном оператором хостинге в РФ. Перенос не выполнен.
3. Проверить необходимость уведомления Роскомнадзора по ст. 22 и, если применимо, вопросы трансграничной передачи по ст. 12. Зафиксировать меры защиты, сроки, порядок ответов/отзывов и удаления данных. Само наличие файлов на сайте не подтверждает выполнение этих обязанностей.
4. Завершить текст политики: фактический хостинг, его журналы, сроки статистики и получатели. Проверить условия Яндекса. Документы сейчас являются проектом под известную архитектуру, а не заключением о полном соответствии закону.
5. Архивировать каждую опубликованную версию документов на сервере оператора. При любом изменении данных, целей, получателей или текста изменить `version`, чтобы старое согласие перестало включать аналитику.
6. После настройки сервера и проверки документов установить `reviewedAndReady: true`, пересобрать сайт и развернуть его. Этот флаг не заменяет перечисленных действий.

## Сервер фиксации согласий

`scripts/privacy-server.mjs` раздаёт `dist/client` и принимает запросы по тому же origin. Node.js 22.13+; HTTPS должен завершаться на обратном прокси. Сервер слушает только `127.0.0.1`. Не публиковать порт напрямую без HTTPS.

```powershell
# Пример для корневого домена: siteUrl в конфигурации заканчивается на /.
# При сохранении пути /landing задать NEXT_PUBLIC_BASE_PATH=/landing.
$env:NEXT_PUBLIC_BASE_PATH = ''
npm run build:pages
$env:CONSENT_DATA_DIR = 'C:/rentzal-private/consents'
$env:PORT = '3000'
npm run start:privacy
```

На Linux те же переменные передаются через окружение процесса. Папка журнала должна находиться вне публичного каталога, на выбранном сервере в РФ. Ограничить права ОС, доступ администраторов и резервные копии. Не хранить журнал в Git или GitHub Actions. Сервер не добавляет IP, User-Agent и поля контактов в записи. Прокси и хостинг могут вести собственные журналы — настроить и раскрыть их отдельно.

API: POST `<base>/api/privacy-consent`, `Content-Type: application/json`, Origin должен совпадать с `siteUrl`:

```json
{"choice":"accepted","version":"2026-09-22.2"}
```

Ответ 201: `{"receiptId":"UUID"}` только после записи и flush файла. Для отзыва: `{"choice":"withdrawn","version":"2026-09-22.2","receiptId":"UUID"}`. Отзыв в браузере немедленно отключает сбор даже при недоступном API. Ранее переданные данные требуют отдельного процесса удаления. Серверный журнал фиксирует получение решения браузера, но не устанавливает личность человека.

Сервис ограничивает размер тела 1 КБ, принимает только актуальную версию и ограничивает общий поток 120 запросами в минуту. Для масштабирования нужна настройка лимитов на прокси и мониторинг ошибок. Если журнал не записался, клиент не запускает Метрику. Суточные журналы очищаются при старте и каждый час после истечения срока: не более 182 дней. Срок хранения резервных копий обеспечивает оператор.

## Проверка

```sh
npm run test:privacy
npx tsc --noEmit --incremental false
npm run build:pages
```

В чистом браузере проверить: до согласия нет запросов к mc.yandex.ru; отказ и закрытие не загружают tag.js; после согласия сервер возвращает 201, затем загружается tag.js и регистрируется просмотр; отказ сохраняется после перезагрузки; отзыв останавливает сбор и в другой вкладке; старое/повреждённое согласие не принимается; при недоступном API и запрете localStorage счётчик не запускается. Проверить мобильный экран и прямое открытие документов с префиксом размещения. Проверку настоящего счётчика завершить отдельным тестовым визитом и проверкой отчёта в аккаунте владельца.

## Источники

### Результаты локальной проверки 22.09.2026

- `npm run test:privacy`: 2 теста прошли, включая запись/отзыв, неверный Origin, старую версию, чрезмерное тело, закрытый журнал и выключенную конфигурацию.
- TypeScript и адресный lint новых/изменённых модулей согласий: без ошибок.
- Полный lint репозитория выявляет существующие замечания в UI-компонентах, `use-mobile`, `chart`, `page` и `product-link`; эти файлы в рамках задачи не исправлялись. В `app/page.tsx` были незакоммиченные изменения до начала работы, они сохранены.
- Production build с `NEXT_PUBLIC_BASE_PATH=/landing`: успешен, все четыре страницы открываются с HTTP 200 через статический сервер. Юридические ссылки сохраняют префикс. На ширине 320 px горизонтального переполнения нет.
- Через подключённый Playwright MCP в изолированном Chrome проверены закрытие без согласия, сохранение отказа, ошибка API, успешная запись перед инициализацией и просмотром, отзыв с удалением cookie, отзыв при отказе записи/удаления localStorage с переходом на другую страницу, истечение срока при запрете удаления, повреждённая и старая запись согласия.
- Для положительных сценариев конфигурация и API подменялись только в тестовом браузере; запрос tag.js перехватывался тестовой заглушкой. Настоящие данные в Яндекс не отправлялись. Проверка живого счётчика и отчётов ещё не выполнена.
